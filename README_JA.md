『Mount & Blade II: Bannerlord』mod の `.tpac` アセットパッケージを別の mod へ一括移行し、
**各パッケージに対応するランタイムキャッシュも一緒に**移行します。
パッケージ内にハードコードされたリソースパスの参照を自動再マップし、
「移行してもゲーム内では空白で、しかもエラーも出ない」問題を解決します。

## 解決する問題

リソースを別の mod へ移行するには、**2 つのもの**を移行する必要があります。どちらが欠けても機能しません。

| 移行するもの | 内容 | 欠けた場合どうなるか |
|---|---|---|
| `Assets/<サブディレクトリ>/*.tpac` | リソースコンテナ：メッシュ、テクスチャ、マテリアルとパッケージ時にハードコードされたソースパスを記述 | ゲーム内でリソースが見つからない |
| `RuntimeDataCache/<GUID>.rdc` | メッシュとテクスチャの**実データ**（tpac には参照のみ、ピクセルデータはない） | アイテムは購入・装備可能、ログにもレンダリング要求あり、**しかしモデルは真っ白で、エラーは一切出力されない** |

このツールは両方を移行します。

### 第一の作業：ハードコードされたパスの書き換え

`.tpac` は TaleWorlds 独自のリソースコンテナです。リソースはパッケージ時にソースパスが埋め込まれます。例：

```
$BASE/Modules/MercenaryVariety/AssetSources/rome_items/mv_armor_coat.fbx
```

このパスは**パッケージと共に移動**します。tpac を別の mod にコピーしても、パッケージ内の参照は元モジュールのままです。これが「mod を変えるとパッケージが機能しなくなる」根本原因です。

ツールはコンテナを解析し、これらの参照をルールに従って新モジュールパスへ書き換えます：

```
$BASE/Modules/MercenaryVariety/  ->  $BASE/Modules/<ターゲットモジュール>/
```

同時に、パッケージ内のリソース間の **GUID 依存関係**（マテリアル → テクスチャ、メッシュ → マテリアルはいずれも GUID 参照でありパス参照ではない）もスキャンし、
どの依存関係がパッケージ外を指しているかをレポートします。移行後に何が不足しているかがわかります。

### 第二の作業：ランタイムキャッシュ（RuntimeDataCache）の同時移行

メッシュとテクスチャの実データは **`.tpac` の中にはなく**、モジュールルートにあります：

```
Modules/<モジュール名>/RuntimeDataCache/82F204BF-0A6C-4F0E-A023-326A2D9D65B1.rdc
                                  └── ファイル名は tpac ヘッダ 8~24 バイトの GUID ──┘
```

ツールは各パッケージの移行時にこのファイル名を自動算出します。**ソースモジュール**の `RuntimeDataCache/` から対応するファイルを探し、
**ターゲットモジュール**の同じ場所へコピーします。ファイル名は変更せず、内容も**書き換えません**——`.rdc` は純粋なバイナリでありパス文字列を含まないため、安全にバイト単位コピーできます。

覚えておくべき 2 つのルール：

- **キャッシュは常にターゲットモジュールのルートに配置**され、`Assets/` のサブディレクトリ階層には従いません。エンジンは `Modules/<モジュール名>/RuntimeDataCache/<GUID>.rdc` を検索するため、キャッシュを `Assets/<サブディレクトリ>/` 配下に置いても無意味です。
- **マテリアルパッケージ（`*_mtl.tpac`）は元々キャッシュを持たない**ため、ツールはエラーを出さずにスキップします。MCV の 62 個の実パッケージで検証した結果：50 個はキャッシュあり、12 個のマテリアルパッケージはキャッシュなし、すべて正確。

### バンドルファイル（`AssetPackages/*.tpac`）は自己完結

`AssetPackages/`（および `EmAssetPackages/`）配下のパッケージは、`Assets/` 配下の単一リソースパッケージとは**別物**です：

| | `Assets/<サブディレクトリ>/xxx.tpac` | `AssetPackages/xxx.tpac` |
|---|---|---|
| 入っているもの | **1 つ**のリソース（メッシュ / マテリアル / テクスチャ） | **多数**のリソース。データを内包 |
| ヘッダ GUID の意味 | **そのリソースの GUID**（= キャッシュファイル名） | **パッケージ形式の GUID**（固定値） |
| 別途 `.rdc` キャッシュが必要か | 必要 | **不要**（データはパッケージ内） |

バンドルファイルのヘッダ GUID は実測で固定です——244 個のバンドルファイルをスキャンしたところ、**243 個が同一の値**
`807E3D8D-E501-499B-A1D3-22AE3F4E64F3`。旧版はこれをリソース GUID と解釈して `RuntimeDataCache/` に
キャッシュを探しに行き、当然見つからないため大きなパッケージをすべて赤文字の「キャッシュ不足」にしていました——誤報です。
現在はこの種のパッケージを認識し、キャッシュ列に**「自己完結」**と表示、赤くならず、整合性の集計からも除外されます。

### `RuntimeDataCache/` の真実

これは mod に同梱されて配布されるもの**ではなく**、Bannerlord エディタが**あなたのマシンでリソースをベイクしたとき**に生成する副産物です。
環境全体をスキャンした実測結果：`RuntimeDataCache/` を持つモジュールは**3 つだけ**（いずれもエディタで焼いた開発機のモジュール）。
公式の **Native / SandBox / NavalDLC、およびネットから直接ダウンロードした mod には一切ありません**。したがって：

- 他人の mod を移行するとき、そもそも移行できるキャッシュが存在しない——**これは異常ではなく通常**です；
- キャッシュが無くても必ずしも真っ白になるわけではありません——初回ロード時にエンジンがパッケージ内 `metadata` の
  指す `AssetSources/<...>/xxx.png` から**自らベイク**します（前提：ソースファイルが存在すること）。
  「キャッシュも無く、ソースファイルも無い」場合だけが本当に壊れています。
- つまり「ソースにキャッシュが無い」は**ヒント**に過ぎず、ツールがこれを理由に移行を止めることは絶対にありません。

### 移行不要なもの：AssetSources

`AssetSources/` は**エディタ用のアセットソースファイル**（fbx、psd など）で、Bannerlord エディタ内でリソースを再ベイクするときにのみ使用されます。**ランタイムロードでは一切参照されません**——ゲームは上記の `.rdc` キャッシュを読みます。したがって移行時には不要で、インターネットからダウンロードした mod パッケージにも通常このディレクトリはありません。「将来もエディタでこのリソースを編集する」場合にのみ保持してください。

### 第三の作業：キャッシュ整合性チェック（ブロックしない）

キャッシュを移行するだけでは不十分です。ツールは 2 つのタイミングで「**必要なものがすべて揃っているか**」を再確認します。**移行はブロックしません**：

| タイミング | 確認内容 | 表示場所 |
|---|---|---|
| スキャン終了時 | 移行対象パッケージのうち、**キャッシュが必要な** N 個に対しソースモジュールに何個揃っているか / 何個不足しているか | ログ + スキャン表の「キャッシュ」列（不足行は**赤色**） |
| 移行完了時 | ターゲットモジュール `RuntimeDataCache/` に今しがた移行したキャッシュがすべて配置されているか | ログ「ターゲットモジュール検証：…」 |

判定ルールはシンプルです：

- **不要 · マテリアル**：`Material` タイプのみのマテリアルパッケージ（ファイル名が `*_mtl.tpac` や `*_material_mtl.tpac` など）
- **不要 · 自己完結**：`AssetPackages/` / `EmAssetPackages/` 配下のバンドルファイル（前節参照）、
  またはヘッダ GUID が既知のパッケージ形式 GUID と一致するもの
- **必要**：残りのすべての単一リソースパッケージ
- **不足**：本来キャッシュが必要だが、ソースモジュールにも対応する `.rdc` が見つからない — 赤で警告

> 上記 2 つの「不要」カテゴリはいずれも整合性集計の**分母から除外**されるため、大きなパッケージが数字を赤一色にすることはありません。

なぜブロックしないのか：実検証で判明 — **初回ロード時**に、エンジンはパッケージ内の `metadata` が指すソースファイル
（`AssetSources/<...>/xxx.png` など）からキャッシュを**自動ベイク**します（前提：`AssetSources/` にソースファイルがあること）。
つまり「ソースにキャッシュがない」ことは「ゲーム内で白くなる」ことを意味しません。**初回ロード時にエンジンがベイクするのを待つだけ**です。

**出力例**：

```
Cache audit: 8 expected, source has 7, missing 1; 2 material package(s) need no cache
    0566A1FC-A449-4DAD-9443-1D54BE030C9E.rdc
Target module check: all 7 caches in place
```

**どの行を見て何を判断するか**：

- ソースで不足だがターゲットで揃っている（= ゲームが既にベイク済み）→ 問題なし、そのまま使用可
- ソースで不足かつターゲットでも不足 → 初回ゲーム起動時にエンジンがベイクする間だけロードが遅くなる。数秒で完了
- 移行後**ターゲット**側で不足（書き込み失敗 / ディスク満杯）→ これは本当に問題発生、上記のエラーログを確認

## 配置先：パッケージはどのサブフォルダに入るか

mod 制作では通常、アイテム種別ごとにリソースを分けて管理します（`rome_items` / `levant_items` / `vaegir_items` …）。
エディタでの管理が楽になるからです。本ツールは**既定でソースの分類をそのまま再現**するため、追加操作は不要です：

| ソース上の位置 | ターゲット上の位置（既定） |
|---|---|
| `…\Assets\rome_items\a_geo.tpac` | `<ターゲットモジュール>\Assets\rome_items\a_geo.tpac` |
| `…\Assets\levant_items\b_geo.tpac` | `<ターゲットモジュール>\Assets\levant_items\b_geo.tpac` |
| `…\AssetPackages\pack0.tpac` | `<ターゲットモジュール>\AssetPackages\pack0.tpac` |

**すべての**パッケージを 1 つのサブフォルダにまとめたい場合（例：散在するものを `rome_items` に集約）は、
GUI の「サブフォルダ」欄に名前を入力、または CLI で `--subdir` を使います：

| 入力値 | 実際の配置先 | 説明 |
|---|---|---|
| `rome_items` | `<ターゲットモジュール>\Assets\rome_items\` | `Assets\` が自動付加されます |
| `Assets\rome_items` | `<ターゲットモジュール>\Assets\rome_items\` | フル指定なら重複付加しません |
| `rome_items\heavy` | `<ターゲットモジュール>\Assets\rome_items\heavy\` | ネストパスも可 |
| `AssetPackages` | `<ターゲットモジュール>\AssetPackages\` | リソースルートとして認識、`Assets\` を重ねません |
| *（空欄）* | ソースの分類を再現 | 既定の動作 |

サブフォルダを指定した場合、それは「ソースの分類を再現」チェックより**優先**され、すべてのパッケージがその 1 ディレクトリに集約されます。

### ターゲットディレクトリを深く選びすぎても安全

エンジンは `Assets\` / `AssetPackages\` の**第 1 階層**のサブフォルダのみをプリロードするため、
さらに `Assets\` を連結すると `Assets\Assets\rome_items\` となり、パッケージは 1 つも読み込まれません。
ツールは結合前にターゲットディレクトリを**モジュールルートへ正規化**します。`<モジュール>\`、
`<モジュール>\Assets\`、さらには `<モジュール>\Assets\rome_items\` を選んでも、結果は常に正しくなります。

## 動作環境

- Windows（ランチャーと GUI は Windows 向け；CLI は純粋な Python）
- Python 3.8 以上、実検証は 3.11
- **GUI は Python 同梱の `tkinter` が必要**（python.org 公式インストーラには同梱；一部の軽量版 / 組込み版 / Microsoft Store 版には含まれていない）
- **サードパーティライブラリは一切不要**：LZ4 block デコードは純 Python 実装。環境に `lz4` がインストールされていれば再圧縮時に使用されますが、なくても完全に動作します（あっても速くなるだけ）

## 使用方法

### GUI（推奨）

**`启动迁移工具.bat`** をダブルクリック、またはコマンドラインから `python migrator_gui.py` を実行。

1. **ソースとターゲット**：移行する mod ディレクトリ（または単一の `.tpac` ファイル）を追加し、ターゲットモジュールディレクトリを選択。
   「ゲームフォルダを探す…」をクリックすると `Modules` からモジュールを選択できます。
   - ターゲットモジュール名は**フォルダ名**から自動推論されます。これが置換先パスを決定します。
   - **「サブフォルダ」を空欄**（推奨）= ソースの分類を再現。ソースの `Assets/rome_items/` は
     ターゲットの `Assets/rome_items/` に配置されます。**入力した場合**（例 `rome_items`）は
     すべてのパッケージを `Assets/rome_items/` に強制集約し、エディタでの分類管理が楽になります。

> ⚠️ **作業前に必ず確認：ターゲットモジュールのフォルダ名は `SubModule.xml` の `<Id>` と一致している必要があります。**
> パッケージ内の `$BASE/Modules/<名前>/AssetSources/...` はどちらか一方にしかマッチしないため、両者が不一致の場合、必ず一方が解決されません。症状は非常に厄介：**アイテムはゲームで購入・装備可能、エンジンログにもレンダリング要求あり、しかしモデルが真っ白でエラーは一切なし**。ツールは不一致を検出すると赤字で警告し、移行開始前に確認ダイアログを出します。
> 修正方法：フォルダ名を `<Id>` と同じ名前に変更（ランチャーは Id で選択状態を記録するため、フォルダ名を変えても選択状態は失われない）。
2. **ソースをスキャン**：すべての tpac、アイテム数、内容構成、パッケージ外依存数、および**「キャッシュ」列**を一覧表示。
   デフォルトで全選択、先頭列をクリックして個別選択可能。
   - 「キャッシュ」列は**4 状態**です：
     - `✓ 6.0 MB` —— ソースモジュールの `RuntimeDataCache/` に対応 `.rdc` が存在し、移行時に一緒にコピーされます
     - `— マテリアル不要` —— マテリアルパッケージは元々キャッシュを持たず、正常です
     - `— 自己完結` —— `AssetPackages/` のバンドルファイル。データはパッケージ内にあり、キャッシュ不要
     - `キャッシュ不足`（**行全体が赤**）—— 本来必要だが発見できず。あくまでヒントで、**移行はブロックしません**
3. **パス再マップルール**：スキャン完了後、**パッケージ内に出現する実際のパス**に基づいてルールが自動提案されます（推測ではない）。
   手動で追加・削除・編集が可能。
4. **オプション**：「上書き前にバックアップ」と「書き込み後に構造を自己検証」は有効のまま推奨。
5. **移行開始**：「ドライラン（書き込みなし）」でターゲットパスとキャッシュの配置先を確認してから実行。
   移行ログには各キャッシュの行き先ががが1行ずつ報告され、最後にサマリが出力されます。例：

   ```
   RuntimeDataCache：32 個追加、0 個上書き、0 個既存、0 個ポリシーでスキップ、8 個ソースに無し（マテリアルパッケージでは通常）、0 個失敗
   ```

問題発生時は「前回の移行をロールバック」で取り消し — 今回の書き込みファイル（**キャッシュも含む**）を削除し、上書き前のバックアップを復元します。

### CLI

```bat
python migrator.py --source "E:\...\Modules\MercenaryVariety\Assets" ^
                   --target "E:\...\Modules\MyMod" --to MyMod
```

主なパラメータ：`--from <ソースモジュール名>`、`--rule "OLD=NEW"`、`--on-conflict rename|overwrite|skip`、
`--dry-run`、`--no-backup`、`--subdir rome_items`（すべてのパッケージを `Assets/rome_items/` に集約。
`--keep-relative` より**優先**）、`--flat`（モジュールルートへフラット配置、分類を保持しない）、
`--deep-scan`（セグメントを深くスキャン。**既定では無効**——後述「大きなパッケージがメモリを爆食いしなくなった理由」参照）、
`--rollback`（前回の移行を取り消し）、`--lang zh|en|ja`。

> 配置先は**既定でソースの分類を再現**します（GUI と同じ）：ソースの `Assets/rome_items/a.tpac` は
> ターゲットの `Assets/rome_items/a.tpac` に配置されます。`--keep-relative` は現在、旧コマンドとの
> 互換用の記法で、指定してもエラーになりません。フラットにしたい場合は `--flat` を使います。

`--dry-run` はまず配置ルールを表示し、続いて各パッケージの tpac 配置先**とキャッシュの配置先**をリスト表示します：

```
  配置：ソースの分類を再現 —— ソースの Assets/rome_items/ はターゲットの Assets/rome_items/ に配置されます
  ...\vaegir_items\vaegir_lord_helm_geo.tpac -> ...\Modules\MyMod\Assets\vaegir_items\vaegir_lord_helm_geo.tpac
      キャッシュ 0566A1FC-A449-4DAD-9443-1D54BE030C9E.rdc  ->  ...\Modules\MyMod\RuntimeDataCache\0566A1FC-....rdc
  ...\AssetPackages\pack0.tpac -> ...\Modules\MyMod\AssetPackages\pack0.tpac
      キャッシュ：不要（AssetPackages のバンドルは自己完結）
```

キャッシュは `--flat` / `--keep-relative` / `--subdir` の影響を受けず、**常にターゲットモジュールのルートに配置**されます。
バンドルファイル（`AssetPackages/*.tpac`）はそもそも移行すべきキャッシュが**ありません**。

### GUI の言語

画面右上で **中文 / English / 日本語** を切り替え可能。選択は `ui_config.json` に保存され、次回起動時に自動的に引き継がれます。

切り替え範囲は 3 層をカバーします。単なるボタン名ではなく：

- GUI コントロール、列ヘッダ、ダイアログ
- 移行プロセス中のログと警告
- 解析 / 再構築のエラーメッセージ

CLI で個別指定可能：`python migrator_gui.py --lang ja`、`python migrator.py --lang ja`。
初回実行で記録がない場合、Windows の表示言語に応じて自動選択（Windows が日本語環境なら日本語）。

## 書き換えの安全性ポリシー

tpac はバイナリコンテナであり、長さを変更するとファイルが破損します。ツールは安全性のレベルに応じて 3 段階で処理します：

| 状況 | 処理 |
|---|---|
| 新旧文字列が**同一長** | バイト単位でそのまま置換、構造長を一切変更しない、ゼロリスク |
| 文字列に** i32 の長前缀付き**（tpac の一般的な記述方法） | 長前缀も同期して書き換え、構造が一貫、可変長対応 |
| 同一長でもなく、長前缀も見つからない | **スキップして明示的に報告**、絶対に無理に変更しない |

コンテナ全体はエントリ単位で再生成されるため、長さを変更しても TOC とデータ領域のオフセットは自動再計算されます。

未変更のリソースセグメントは**圧縮バイトごとそのまま転送**され、不要な解凍 / 再圧縮は行いません。
変更面が最小限に抑えられるため、数百 MB のパッケージも処理可能（セグメント単位のストリーム読み書きで、ファイル全体をメモリに読み込まない）。

### 大きなパッケージ（数百 MB〜数 GB）がメモリを爆食いしなくなった理由

以前は落とし穴がありました：2.8 GB の `core_game.tpac` を移行すると、プロセスのピークワーキングセットが
**4.6 GB** に達していました。

実測の結果、**互いに独立した 2 つの原因**があり、片方だけ直しても不十分だと分かりました：

1. **書き込み後の構造セルフチェック**：各セグメントを解凍して「解凍後の長さが正しいか」を確認しますが、
   データ取得に使う `get_data()` が解凍結果を**セグメントオブジェクトに永久キャッシュ**します。
   そのため 23109 個のセグメントがすべてメモリに残り、パッケージ全体を解凍したまま抱える状態でした。
2. **セグメント走査（ディープスキャン）**：「万一パスがリソースセグメントに隠れているかも」という保険で、
   4 MB 以下のセグメントをすべて解凍し、これもメモリに保持していました。

同一マシン・同一ファイルでの 4 通りの実測（書き換え数は常に 2010 で、挙動は変わっていません）：

| 構成 | ピークメモリ | 所要時間 |
|---|---|---|
| セグメント走査**有効** + 旧セルフチェック | 4467 MB | — |
| セグメント走査**無効** + 旧セルフチェック | 4609 MB | 212 秒 |
| セグメント走査**有効** + 新セルフチェック | 4483 MB | 447 秒 |
| **セグメント走査無効 + 新セルフチェック（既定設定）** | **150 MB** | 239 秒 |

2 行目と 3 行目が示すとおり、**両方直す必要がありました**。修正後、ピークは**最大の 1 セグメント**にのみ
依存し、セグメント数には依存しません。つまりどんなサイズでも処理できます。

したがって**セグメント走査を既定で無効にしても安全**です。同一パッケージで走査の有無を比較しても
**書き換え結果は完全に一致（どちらも 2010 箇所）**でした。パス文字列はすべて `metadata` にあり、
セグメント走査は 1 箇所も余分に見つけていません。無効にするとメモリ 4.3 GB と 200 秒余りを節約できます。
特殊な構造のパッケージに遭遇した場合は、GUI の「セグメントを深くスキャン」（CLI `--deep-scan`）を
保険として使えます。

この 2.8 GB の `AssetPackages/core_game.tpac` は正常に移行できます：5045 アイテム、
2010 箇所のパス書き換え、所要時間は約 235 秒、出力は再解析してもアイテム数が一致します。

`.rdc` キャッシュは完全に非解析・非書き換えで、バイト単位でそのままコピーされます。

### キャッシュ衝突の処理方法

キャッシュファイル名がそのままエンジンの検索キーとなるため、**ファイル名変更不可**です（`<GUID>_1.rdc` のような名前に変更するとエンジンが発見できない）。ツールの処理は：

| ターゲットモジュールに同名キャッシュが既存 | 処理 |
|---|---|
| 内容完全一致 | スキップ、何十 MB もの重複コピーを回避 |
| 内容不一致 | バックアップ後に上書き（`--on-conflict skip` 指定時は既存ファイル保持） |

## 注意事項

- ツールが行うのは 2 つだけ：tpac 内部のパス参照の書き換え、対応する `.rdc` キャッシュの転送。
  **XML 内のリソース参照**（`ModuleData` 配下のアイテム、兵種など）は tpac 内にはありません。手動で名前を同期するか、
  ターゲットモジュールに元のリソース名を使い回してください。
- スキャンレポートに「外部依存 GUID」が表示される場合、それらのリソースがこのパッケージ外のものを参照しています。
  ターゲット環境でも同様に解決できる必要があります。そうでないとモデルは表示されません — この種の依存関係は通常、マテリアル / テクスチャがソース mod または元版に残されているケースで、一緒に移行する必要があります。
- 移行はターゲットディレクトリのみ書き込み、**ソース mod は変更しません**。ただし初回の一括操作の前には、ターゲットモジュールのバックアップを推奨します。
- ターゲットモジュールに既に同名キャッシュが存在し内容が異なる場合は、バックアップ後に上書きされます。
- 重要でないパッケージで先にテストし、ゲーム内で問題がないことを確認してから一括実行することを推奨します。

## フォーマット仕様

コンテナフォーマットは TpacTool（szszss / hunharibo、MIT）のリバース結果を参考にし、実際のリソースパッケージで検証：

```
ヘッダ 36B: magic "TPAC" | version | package guid | エントリ数 | データ領域オフセット | 予約
エントリ:     type guid | item guid | version | 名前(長前缀) | metadata 長 | metadata
              | チェックサム | セグメント数 | セグメント[] | 依存数 | 依存[]
セグメント:   オフセット | 元サイズ | 保存サイズ | owner guid | type guid | 未知×2 | 保存形式
保存形式:     0 = 生、1 = LZ4-HC
```

ヘッダの **package guid**（オフセット 8~24）は同時にランタイムキャッシュのファイル名も決定します：
.NET Guid のテキスト形式（最初の 3 セグメントはリトルエンディアン）で大文字出力し、`.rdc` 拡張子を付加。

> **1 つ例外があります**：このフィールドは**単一リソースパッケージ**（`Assets/<サブディレクトリ>/xxx.tpac`）では
> 確かにリソース GUID ですが、**バンドルファイル**（`AssetPackages/xxx.tpac`）では**パッケージ形式の GUID** です
> （実測：244 個中 243 個が `807E3D8D-E501-499B-A1D3-22AE3F4E64F3` と同一）。バンドルファイルは自己完結で
> 対応するキャッシュが存在しないため、この値で `RuntimeDataCache/` を探してはいけません——ツールはまさに
> この特徴で「自己完結」パッケージを識別しています。

ツールには純 Python の LZ4 block デコードが内蔵されており、サードパーティライブラリは不要です；
環境に `lz4` がインストールされていれば再圧縮時に使用されますが、なくても正常に動作します。
